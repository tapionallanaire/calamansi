# 3DS HOME UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the approved 3DS-inspired Azahar UI with top-screen selected-game preview, bottom-screen HOME tiles/actions, matching app chrome and a complete single-display fallback.

**Architecture:** Keep MainActivity and its existing NavController on the primary display. A persistent Activity-owned GamesFragment owns the lower HOME Presentation and one active library adapter/host. The upper NavHost switches selected-game preview, Search, All Apps or Options without destroying that library. Share only display-selection policy with emulation; never share native surfaces or emulator settings.

**Tech Stack:** Kotlin, XML/ViewBinding, Android Presentation/DisplayManager, existing AndroidX RecyclerView/Navigation/ViewModel/StateFlow, Material components and Coil; Python standard library plus adb for device verification. No new product dependencies.

**Spec:** `docs/superpowers/specs/2026-10-10-3ds-home-ui-design.md` (approved by user).

## Global Constraints

- Preserve the Fates Vulkan/HD portrait fixes, opt-in bloom reduction, FXAA, sparse per-game settings, cartridge support, shared `/sdcard/citra-emu` access and all saves.
- Do not change graphics defaults, emulator screen-layout settings, game performance presets, firmware or save formats.
- Games, Search, All Apps and Options use the user's requested fixed classic silver-white/mint theme. Preserve stored theme preferences for separate settings/emulation activities; do not overwrite them.
- No fake eShop/Miiverse apps, invented artwork, new fonts, asset downloads or continuously animated backgrounds.
- Every interactive target is at least 48dp; tiles have at least 72dp interactive bounds.
- HOME does not instantiate SecondaryDisplay, create HiddenDisplay, call native secondary-surface/touch methods, or read/write enable_secondary_display/secondary_display_layout.
- No background render loop, permanently held wake lock, periodic game scanning or animated 3D HOME scene.
- Android build retains minSdk 29, existing ABIs/build variants and installed dependencies. Preserve all existing uncommitted user work.
- No temporary diagnostics in final sources/APKs. No claim of unexercised hardware or full-suite success.

## Review Focus

1. Same-title/same-ID games at different paths and reloaded Game objects: selection/actions must follow path and latest visible metadata, not holder/index identity. Task 1 pins this in the standalone selection check.
2. Late display callbacks during game launch/background/screen sleep: HOME must not reopen over native emulation. Task 2 owns guarded eligibility; Task 4 exercises handoff and sleep/wake window counts.
3. Nested properties dialogs and returning from settings/cheats: releasing a sheet must not reactivate HOME before the modal chain/navigation handoff finishes. Task 2 owns the modal guard; Task 4 opens properties/actions and verifies HOME ownership.
4. Large fonts, RTL, display-specific width/insets and theme recreation: controls remain visible/reachable, with no primary-width assumptions on the bottom display. Task 3 owns resources; Task 4 captures these actual surfaces and restores changed preferences.
5. Deleted files, invalid/encrypted ROMs and direct URI/system-title launch: the new HOME action must reject a missing file without gating independent emulator entry on library selection or Game.valid. Task 1 owns the launch guard; Task 4 exercises a nonce-owned missing-file entry and existing decrypted .3ds/direct-entry paths.

fun launchGame(game: Game) {
    if (!gameExists(game)) return

    if (now - lastClickTime < 1000) return

}
